# swc-ssr: server-side rendering for Spectrum Web Components

Server-side rendering and hydration for [Adobe Spectrum Web Components](https://github.com/adobe/spectrum-web-components)
(1st-gen, `@spectrum-web-components/*` 1.12.4), built as a plugin for [`@lit-labs/ssr`](https://lit.dev/docs/ssr/overview/)
4.1.0. It renders Spectrum elements to declarative shadow DOM on the server and hydrates that markup in the browser
without a visible change.

* No Spectrum source is modified and nothing under `node_modules` is patched. Everything goes through Lit SSR's extension
  points (element renderers), a DOM-shim extension, per-tag adapters and client hydration hooks.
* This is an independent project. It is not affiliated with, endorsed by or maintained by Adobe.
* Status: 55 of 59 catalog entries render, hydrate without errors and without flicker, and match the client-rendered DOM;
  see [the support matrix](../../tests/results/summary.md) (generated by the Playwright suite in `tests/`) and
  [Limitations](#limitations).

The package is not on npm yet. In this repository it is the workspace package `swc-ssr`; the suggested public name is
`spectrum-web-components-ssr`. The examples use the workspace name (`swc-ssr/server`); substitute the published name.

## Install

```sh
npm install spectrum-web-components-ssr
npm install lit lit-html lit-element @lit-labs/ssr @lit-labs/ssr-client @lit-labs/ssr-dom-shim
npm install @spectrum-web-components/bundle
```

`lit`, `lit-html`, `lit-element` and the three `@lit-labs` packages are peer dependencies: your application and this
package must share one copy of each (a second copy of `lit-html` breaks hydration). `@spectrum-web-components/base` is an
optional peer; the adapters were written and tested against 1.12.4, other versions are untested. Requires Node 20 or
newer (developed and tested on Node 22) and, for types, a TypeScript `moduleResolution` of `node16`, `nodenext` or
`bundler` (the package uses an `exports` map).

The package has three entry points, all ES modules:

| Entry | Runs in | Purpose |
|---|---|---|
| `swc-ssr/server` | Node | `renderSpectrum()` and the adapter registry. Importing it installs the DOM shim. |
| `swc-ssr/dom-shim` | Node | the DOM globals Spectrum needs under Node (also pulled in by `/server`). |
| `swc-ssr/client` | browser | `hydrateSpectrum()` and hydration adapters. Bundle it with your application. |

## Server

```ts
// The first import of the server: importing it installs the DOM shim, which must exist before `lit` or any
// @spectrum-web-components module is evaluated.
import {installSpectrumSsr, renderSpectrum} from 'swc-ssr/server';
import {html} from 'lit';

installSpectrumSsr(); // explicit and idempotent; the import above already did the work
await import('@spectrum-web-components/theme/sp-theme.js');
await import('@spectrum-web-components/theme/src/themes.js');
await import('@spectrum-web-components/button/sp-button.js');

const {html: markup, report} = await renderSpectrum(
  html`<sp-theme system="spectrum" color="light" scale="medium"><sp-button>Save</sp-button></sp-theme>`,
  {deferHydration: true, lang: 'en'},
);
// report.elements: per element errors / warnings / fallback; report.passes: 2 or 3; report.durationMs
```

Import Spectrum modules by bare specifier (`@spectrum-web-components/button/sp-button.js`), never by file URL: a second
evaluation of a module makes `customElements.define` throw on the duplicate.

`renderSpectrum(value, options)` takes anything `@lit-labs/ssr` renders (a `TemplateResult`, a string, an iterable) and
resolves to `{html, report}`. It renders in two passes: the first collects the element tree, the second renders every
element with access to its light DOM, slots and shadow content, which Spectrum components depend on. A third pass runs
when an element failed in pass 2 without tree information, or changed after its markup was emitted. Renders are queued one at a time because the DOM shim and the
element registry are process-wide.

| Option | Default | Meaning |
|---|---|---|
| `deferHydration` | `false` | forwarded to `@lit-labs/ssr`: adds `defer-hydration` so nothing hydrates before the client says so. Use `true` with `hydrateSpectrum()`. |
| `lang` | none | the page's `<html lang>` during the render, restored afterwards. Components format numbers and pick labels from it. Without it the server resolves `navigator.language` (`en-US`) and the report warns `locale: no language is set`. Pass the same language you write to `<html lang>`. |
| `lifecycle` | `'full'` | lifecycle of Spectrum elements: `'none'` (Lit default), `'connected'`, or `'full'` (also `firstUpdated`/`updated`, the rAF queue and a bounded re-render, so the markup shows the settled state). |
| `lifecycleByTag` | none | per-tag override, also opts non-Spectrum Lit elements in: `{'sp-overlay': 'none', 'my-element': 'full'}`. |
| `isManagedClass` | Spectrum classes | which classes get `lifecycle` by default. Other Lit elements keep upstream `@lit-labs/ssr` semantics. |
| `elementRenderers` | none | extra `ElementRenderer`s tried before the Spectrum ones. |
| `timeoutMs` | `10000` | deadline of one render; `0` or `Infinity` disables it. A render that does not settle returns its last completed pass plus a warning. |
| `lazyDefinitionWaitMs` | `250` | how long to wait for definitions that components import lazily (`sp-slider` imports `sp-number-field` in `render()`). |
| `deterministicIds` | `true` | Spectrum's `randomID()` ids are deterministic per render. `false` uses the CSPRNG for this render. |
| `debug` | `false` | keep the `data-swc-ssr` markers and log details. |

### Adapters

Everything specific to one component lives in an adapter. Built in: `sp-theme`, `sp-overlay` (kept closed), `sp-picker`,
`sp-breadcrumbs`, `sp-split-view`, `sp-color-wheel`. Register your own, or replace a built-in one (the last registration
for a tag wins):

```ts
import {registerAdapter} from 'swc-ssr/server';

registerAdapter({
  tag: /^my-/, // a tag name or a RegExp
  lifecycle: 'connected', // cap for matching elements
  prepare(element, ctx) {}, // every pass, right after the instance exists, before attributes and lifecycle
  beforeRender(element, ctx) {}, // pass 2 and later, before render()
  afterRender(element, ctx) {}, // pass 2 and later
});
```

`ctx` carries `pass`, `id`, the structural `key`, the `ServerTree` and the element's `report` entry. The full contract is
in [docs/API.md](../../docs/API.md) of the repository.

## Browser

```ts
import 'swc-ssr/client'; // FIRST import of the client bundle: before lit and before any Spectrum module
import {hydrateSpectrum} from 'swc-ssr/client';
import '@spectrum-web-components/theme/sp-theme.js';
import '@spectrum-web-components/theme/src/themes.js';
import '@spectrum-web-components/button/sp-button.js';

const report = await hydrateSpectrum(document.getElementById('app')!);
// report: {errors, warnings, deferred, hydratedCount, durationMs}; hydrateSpectrum never rejects
```

`swc-ssr/client` must be evaluated before `lit`: it installs Lit's hydration support, which `lit-element` reads once,
when the `LitElement` class is created. Evaluate it later and elements ignore `defer-hydration` and re-render their
declarative shadow root from scratch (visible flicker). It also applies the declarative shadow DOM polyfill
(`@webcomponents/template-shadowroot`) when the browser lacks native support.

Two ways to hydrate, chosen by the `template` option:

* **With the Lit template** (the page is a Lit template, rendered by the same template on the server):
  `hydrateSpectrum(root, {template})` calls `hydrate(template, root)` from `@lit-labs/ssr-client`. The template must equal
  the one rendered on the server.
* **Without a template** (framework-agnostic: Angular, plain HTML, anything that produced the markup):
  `hydrateSpectrum(root)` removes `defer-hydration` top-down in document order, after `customElements.whenDefined` for
  the tags it finds. Elements without a `sp-` prefix that were server-rendered, such as `<overlay-trigger>`, are
  included. Tags that never get defined, such as an Angular component host `<app-root>`, are not awaited.

`registerHydrationAdapter({tag, beforeHydrate, afterHydrate, slotchangePlan})` is the client twin of the server adapters:
code around an element's first ("hydrating") update. Built in: `sp-picker`, `sp-slider`, `sp-breadcrumbs`, `sp-checkbox`
and a `matchMedia` adapter for `sp-picker`, `sp-action-menu`, `sp-contextual-help`.

Server output rendered with `deferHydration: true` hydrates its light-DOM elements in document order, which is the order a
client-side render creates them in. Bundling: the e2e suite bundles the client with esbuild and the production conditions
of Lit (no `development` condition); the development builds of Lit are not covered by the tests.

## Frameworks

### Express (what the demo does)

```ts
import express from 'express';
import {renderSpectrum} from 'swc-ssr/server'; // before anything that imports Spectrum
import {html} from 'lit';

const page = () => html`<sp-theme system="spectrum" color="light" scale="medium"><sp-button>Save</sp-button></sp-theme>`;

const app = express();
app.get('/', async (_req, res) => {
  const {html: markup} = await renderSpectrum(page(), {deferHydration: true, lang: 'en'});
  res.type('html').send(
    `<!doctype html><html lang="en"><head><meta charset="utf-8"><title>App</title></head>` +
      `<body><div id="app">${markup}</div><script type="module" src="/client.js"></script></body></html>`,
  );
});
```

`demo/src/server.ts` in the repository is a complete example: page language from `?lang=` / `Accept-Language`, a report
endpoint, client-only reference routes.

### Angular SSR

What is covered by the tests: server-rendered Spectrum markup that is hydrated **without** a Lit template
(`tests/agnostic.spec.ts`, `?agnostic=1` in the demo). What is not: Angular's own server renderer. It does not use Lit,
so Spectrum elements in its output are plain elements without a shadow root. This package does not hook into Angular.

* **Where to install the shim.** Make `import 'swc-ssr/server'` the first import of the server entry (`server.ts` /
  `main.server.ts` of `@angular/ssr`), before any module that imports `@spectrum-web-components/*`, including your own
  component library. Importing it is enough; `installSpectrumSsr()` is the explicit form. The package declares
  `sideEffects` for its server entry so bundlers (the Angular esbuild builder included) keep that import.
* **`window` becomes defined for the whole process.** The shim defines `window` (= `globalThis`), `navigator`, `matchMedia`
  and friends permanently. Libraries that check `typeof window` to detect a browser take their browser branch
  afterwards: import them before the shim, or render Spectrum in a `worker_threads` worker and keep the Angular process
  clean. Neither variant is tested here.
* **Getting Spectrum into the HTML.** `renderSpectrum()` renders Lit templates. A string of HTML from another framework
  can be rendered as a static template (checked in-process with `<sp-theme>` and `<sp-button>`; only attributes carry
  over, not framework property bindings, and fragments only, not whole documents):

  ```ts
  const strings = Object.assign([fragment], {raw: [fragment]}) as unknown as TemplateStringsArray;
  const {html: rendered} = await renderSpectrum(html(strings), {deferHydration: true, lang});
  ```

  Reuse the same `strings` array for the same fragment: Lit caches templates by array identity.
* **Hydration in the browser.** The first import of `main.ts` is `import 'swc-ssr/client'`; load the element definitions,
  then call `await hydrateSpectrum(document.body)` without a template (after or independent of Angular's own
  bootstrap and hydration).

## Limitations

* **Process-wide state.** `installSpectrumSsr()` installs browser-like globals for the whole process and never removes
  them (scoping them to a render is not feasible). Renders are serialized in one queue.
* **Late work after a render.** Some Spectrum code keeps running asynchronously (a disabled `sp-slider`'s
  `handleDisabledChanged()`, `sp-action-menu`'s `manageSelection()`). Rejections that arrive while the render runs become
  report warnings; later ones are only logged in debug mode. A `node:test` runner with its own `unhandledRejection`
  listener still sees them. The package installs one `unhandledRejection` listener with the first render.
* **Layout-dependent state is approximated.** Tabs indicator, color handles and split-view sizes are computed without
  layout and corrected after hydration (`sp-tabs` 0.069 %, `sp-color-area` 0.174 %, `sp-split-view` 0.057 % changed
  pixels in the matrix).
* **Phones.** The server's `matchMedia` never matches, so the server always renders the desktop state. Phones hydrate it
  without a mismatch and re-render into the mobile state (tray, `mobile-view`, modal contextual help) on the next update.
* **Known differences from a client render** (the four red entries of the matrix): `sp-picker` and `sp-breadcrumbs` put the
  roving `tabindex="0"` on the selected menu item after hydration (a client render puts it on the first item);
  `sp-swatch` carries an extra `focusable` attribute on the selected swatch; `sp-table` inserts its checkbox cells at
  runtime, so they appear only after hydration (1.4 % pixel change, reported as `dropped DOM change` warnings).
* **Locale.** Pass `lang` (or set `<sp-theme lang>`); otherwise numbers format as `en-US`.
* **Generated ids.** Module-level counters in Spectrum (`sp-dialog-label-N`) make the first and later renders of one
  process differ slightly in a few ids.
* **Browsers.** The Playwright suite runs in Chromium only.
* **Lit versions.** The package imports `lit-element/private-ssr-support.js` and `lit-html/private-ssr-support.js`; those are
  private to Lit, so keep `lit` within the declared peer range.

## Building and publishing this package

The workspace manifest exports TypeScript sources (`./src/*.ts`) so the demo and the tests run through `tsx` without a
build. The published form exports `./dist/*.js` with `types` conditions. `scripts/` in the repository switches between them:

```sh
npm run build:pkg        # tsc -p packages/swc-ssr/tsconfig.build.json -> packages/swc-ssr/dist (gitignored)
npm run pkg:verify       # builds, packs, installs the tarball into a scratch dir, renders and type-checks from it, cleans up
npm run pkg:prepare      # package.json exports -> ./dist (backup: package.json.orig); add "-- --name <npm-name>" to rename + make public
npm run pkg:restore      # back to the workspace manifest, byte for byte
npm run clean:pkg        # delete dist
```

Release checklist: replace the `REPLACE_WITH_OWNER` placeholders in `package.json`, `npm run pkg:verify`, then

```sh
npm run build:pkg
node scripts/prepare-publish.mjs --name spectrum-web-components-ssr
npm publish ./packages/swc-ssr --access public --dry-run   # drop --dry-run to publish
npm run pkg:restore
```

`sideEffects` lists the whole `dom-shim`, `client` and `server` directories: all of them install globals or register
adapters when evaluated, so they must survive tree shaking.
