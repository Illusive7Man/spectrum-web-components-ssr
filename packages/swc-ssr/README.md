# spectrum-web-components-ssr: server-side rendering for Spectrum Web Components

Server-side rendering and hydration for [Adobe Spectrum Web Components](https://github.com/adobe/spectrum-web-components)
(1st-gen, `@spectrum-web-components/*` 1.12.4), built as a plugin for [`@lit-labs/ssr`](https://lit.dev/docs/ssr/overview/)
4.1.0. It renders Spectrum elements to declarative shadow DOM on the server and hydrates that markup in the browser
without a visible change.

* No Spectrum source is modified and nothing under `node_modules` is patched. Everything goes through Lit SSR's extension
  points (element renderers), a DOM-shim extension, per-tag adapters and client hydration hooks.
* This is an independent project. It is not affiliated with, endorsed by or maintained by Adobe.
* Status: 56 of 59 catalog entries render, hydrate without errors and without flicker, and match the client-rendered DOM;
  see [the support matrix](../../tests/results/summary.md) (generated by the Playwright suite in `tests/`) and
  [Limitations](#limitations).

The npm package is `spectrum-web-components-ssr`. Inside this repository the same package is the workspace package
`swc-ssr` (the demo and the tests import `swc-ssr/...`); every example below uses the npm name.

## Install

```sh
npm install spectrum-web-components-ssr
npm install lit@3.3.3 lit-html@3.3.3 lit-element@4.2.2 @lit-labs/ssr@4.1.0 @lit-labs/ssr-client@1.1.8 @lit-labs/ssr-dom-shim@1.6.0
npm install @spectrum-web-components/bundle@1.12.4
```

`lit`, `lit-html`, `lit-element` and the three `@lit-labs` packages are peer dependencies, which is why the second line
names them: your application and this package must share one copy of each (a second copy of `lit-html` breaks
hydration), and npm does not install peers on its own. The versions are the ones this package is developed and tested
against. Name `@lit-labs/ssr` explicitly: the peer range is `~4.1.0` (4.1.x patch releases only) because the renderers
rely on internals of 4.1.0 - the marker of an element binding passed to renderers as a static attribute, the way
`customElementHostStack` is pushed and popped around `renderShadow()`, and `lib/render.js` `renderThunked` - which a
minor release may change; a bare `npm install @lit-labs/ssr` would take whatever is latest. `@spectrum-web-components/base`
is an optional peer; the adapters were written and tested against 1.12.4, other versions are untested. Requires Node 20
or newer (developed and tested on Node 22) and, for types, a TypeScript `moduleResolution` of `node16`, `nodenext` or
`bundler` (the package uses an `exports` map).

The package has three entry points, all ES modules:

| Entry | Runs in | Purpose |
|---|---|---|
| `spectrum-web-components-ssr/server` | Node | `renderSpectrum()` and the adapter registry. Importing it installs the DOM shim. |
| `spectrum-web-components-ssr/dom-shim` | Node | the DOM globals Spectrum needs under Node (also pulled in by `/server`). |
| `spectrum-web-components-ssr/client` | browser | `hydrateSpectrum()` and hydration adapters. Bundle it with your application. |

## Server

```ts
// The first import of the server: importing it installs the DOM shim, which must exist before `lit` or any
// @spectrum-web-components module is evaluated.
import {installSpectrumSsr, renderSpectrum} from 'spectrum-web-components-ssr/server';
import {html} from 'lit';

installSpectrumSsr(); // explicit and idempotent; the import above already did the work
await import('@spectrum-web-components/theme/sp-theme.js');
await import('@spectrum-web-components/theme/src/themes.js');
await import('@spectrum-web-components/button/sp-button.js');

const {html: markup, report} = await renderSpectrum(
  html`<sp-theme system="spectrum" color="light" scale="medium"><sp-button>Save</sp-button></sp-theme>`,
  {deferHydration: true, lang: 'en'},
);
// report.elements: per element errors / warnings / fallback; report.passes: 2 or 3; report.durationMs
```

Import Spectrum modules by bare specifier (`@spectrum-web-components/button/sp-button.js`), never by file URL: a second
evaluation of a module makes `customElements.define` throw on the duplicate.

`renderSpectrum(value, options)` takes anything `@lit-labs/ssr` renders (a `TemplateResult`, a string, an iterable) and
resolves to `{html, report}`. It renders in two passes: the first collects the element tree, the second renders every
element with access to its light DOM, slots and shadow content, which Spectrum components depend on. A third pass runs
when an element failed in pass 2 without tree information, or changed after its markup was emitted. Renders are queued one at a time because the DOM shim and the
element registry are process-wide.

| Option | Default | Meaning |
|---|---|---|
| `deferHydration` | `false` | forwarded to `@lit-labs/ssr`: adds `defer-hydration` so nothing hydrates before the client says so. Use `true` with `hydrateSpectrum()`. |
| `lang` | none | the page's `<html lang>` during the render, restored afterwards. Components format numbers and pick labels from it. Without it, a whole-document template uses its own `<html lang>`; otherwise the server resolves `navigator.language` (`en-US`) and the report warns `locale: no language is set`. Pass the same language you write to `<html lang>`. |
| `lifecycle` | `'full'` | lifecycle of Spectrum elements: `'none'` (Lit default), `'connected'`, or `'full'` (also `firstUpdated`/`updated`, the rAF queue and a bounded re-render, so the markup shows the settled state). |
| `lifecycleByTag` | none | per-tag override, also opts non-Spectrum Lit elements in: `{'sp-overlay': 'none', 'my-element': 'full'}`. |
| `isManagedClass` | Spectrum classes | which classes get `lifecycle` by default. Other Lit elements keep upstream `@lit-labs/ssr` semantics. |
| `elementRenderers` | none | extra `ElementRenderer`s tried before the Spectrum ones. |
| `timeoutMs` | `10000` | deadline of one render; `0` or `Infinity` (or anything from 2^31 ms on) disables it. A render that does not settle returns its last completed pass plus a warning. |
| `lazyDefinitionWaitMs` | `250` | how long to wait for definitions that components import lazily (`sp-slider` imports `sp-number-field` in `render()`), once per tag and process: tags still undefined when the wait ends are never waited for again. Never beyond `timeoutMs`. `0` disables the wait; `Infinity` waits up to the render's deadline (when it passes, that render returns its first-pass output with a warning; a client-only element that is never defined on the server costs this once per process). Without a deadline (`timeoutMs: 0`), `Infinity` means the default 250 ms. |
| `deterministicIds` | `true` | Spectrum's `randomID()` ids are deterministic per render. `false` uses the CSPRNG for this render. Note: every plain `Uint8Array(4)` `getRandomValues` request made synchronously during a render gets deterministic bytes (the shape of `randomID()`'s request), also from your own template code; never use such bytes for secrets there, or turn this off. |
| `debug` | `false` | keep the `data-swc-ssr` markers and log details. |
| `styles` | `{mode: 'full'}` | the CSS of the declarative shadow roots. `{mode: 'trimmed'}` keeps only what the rendered page can use; see [Smaller pages](#smaller-pages-trimmed-css). Trimmed pages require `spectrum-web-components-ssr/client`. `{dedupe: 'link'}` (any mode) links one copy of each stylesheet instead of repeating it; see [One copy per stylesheet](#one-copy-per-stylesheet-dedupe-link). |

### Smaller pages: trimmed CSS

In the default `full` mode every shadow root carries its element's complete stylesheets: about 95 % of the HTML of a
Spectrum page is CSS. `styles: {mode: 'trimmed'}` keeps, per stylesheet, the rules whose selectors can match the
rendered DOM of that stylesheet's instances on this page (`:hover`, `:focus-visible`, `:checked` and other state
pseudo-classes count as matching), the at-rules they need, and only the theme custom properties that something on the
page uses, transitively.

```ts
import {renderSpectrum, scanCustomPropertyReferences} from 'spectrum-web-components-ssr/server';

const {html: markup, report} = await renderSpectrum(page(), {
  deferHydration: true,
  lang: 'en',
  styles: {
    mode: 'trimmed',
    references: scanCustomPropertyReferences(appCss), // theme variables your own CSS reads ('--spectrum-*' works too)
    minifyCustomProperties: true,                     // optional: short custom-property names
  },
});
console.log(report.styles); // {mode, sheets: [{id, tag, instances, fullBytes, trimmedBytes, hash?}], fullBytes, trimmedBytes, durationMs, dedupe?}
```

| Option | Default | Meaning |
|---|---|---|
| `mode` | `'full'` | `'trimmed'` turns trimming on. |
| `trimTheme` | `true` | prune the theme's custom-property declarations nothing on the page uses. |
| `references` | none | custom-property names (or `--prefix-*`) your own CSS uses: kept with their dependencies, never renamed. A single string is one entry. |
| `undefinedPrefixes` | `[]` | prefixes your app never defines, e.g. `['--mod-']`: `var(--mod-x, V)` becomes `V`. |
| `minifyCustomProperties` | `false` | rename custom properties to `--a`, `--b`, ...: names only the theme defines, or that live inside one component's stylesheets. Never Spectrum's public `--mod-*` / `--highcontrast-*` / `--system-*` (your overrides keep working), never names one component defines for another, or that another component's complete stylesheet uses. Unsafe when your app sets or reads `--spectrum-*` itself without listing them in `references`. |
| `keep` | none | selectors (substring or RegExp) whose rules are always kept. |
| `dedupe` | `'none'` | `'link'`: every distinct stylesheet text is stored once and linked from each shadow root; see [One copy per stylesheet](#one-copy-per-stylesheet-dedupe-link). Works in `full` mode too. |
| `dedupeUrl` | `/swc-css/<hash>.css` | with `dedupe: 'link'`: `(hash, css) => url` of a stored text (e.g. to upload it to a CDN). |

Measured: button page 1.22 MB -> 0.83 MB trimmed -> 0.47 MB minified (gzip 120 -> 79 -> 15 KB, brotli 44 -> 12 -> 10 KB);
picker 1.32 -> 0.52 -> 0.39 MB; the whole 59-component catalog 18.66 -> 13.31 -> 9.10 MB. Trimming takes 9-23 ms on a one-component page and
about half a second on the catalog. Every `<style>` the trimmer changed carries `data-swc-styles="trimmed"` /
`"minified"` (`STYLE_MARKER_ATTRIBUTE`).

**Trimmed pages require `spectrum-web-components-ssr/client`.** Lit's hydration support keeps a hydrated element's server `<style>` as its
only stylesheet (it adopts nothing for a declarative shadow root), and `<sp-theme>` drops its server `<style>` and adopts
the complete theme when it upgrades. Without the client a trimmed page breaks on the first state change after hydration
(the rules were trimmed away), and a minified page loses its theme values as soon as `<sp-theme>` upgrades.
`spectrum-web-components-ssr/client` gives every hydrated element its class's complete stylesheets back in the same task as its hydrating
update, on both the template and the agnostic path, and keeps the server's theme `<style>` until the last element is
restored, and only from themes that have upgraded (a theme defined late, or never, keeps its server CSS; minified
elements wait for it). While `sp-theme` is undefined, content created on the client lacks the theme values the server
left out; `hydrateSpectrum()` warns `theme pending: ...`. If your app defines `sp-theme` late, use `trimTheme: false`
and no minification. Define `sp-theme` after its theme fragments, and parent components before their children
(`sp-sidenav` before `sp-sidenav-item`), in one task when you split your bundle. What else trimming can break (application CSS that reads theme variables, state changes before
hydration, minification and app-defined `--spectrum-*` overrides): see docs/API.md "Styles" in the repository. Two
things to know:

- **Attributes a component sets in `connectedCallback()`** are not in the server output, so trimmed CSS has no
  `:host([attr])` rules for them between the element's definition and its hydration (the hydrating update restores
  the complete sheets). If that window is visible in your app (a late `hydrateSpectrum()`, lazy hydration), list such
  selectors in `keep`.
- **Build-time custom-property renamers** (an "unused CSS" step that renames or drops custom properties in your built
  bundle) must process the SSR server bundle too, or be disabled while this package renders - in `full` mode as well.
  Otherwise the server writes the original names, the client's `<sp-theme>` defines the renamed ones when it upgrades,
  and the page that looked right from the server goes unstyled at hydration. `minifyCustomProperties` handles both
  sides and is the supported way to get short names.

### One copy per stylesheet: `dedupe: 'link'`

Every shadow root carries its own `<style>` copy of its component's stylesheets: the button page repeats one 36 KB
`sp-button` sheet 21 times, the catalog carries 0.6-1.9 MB of distinct CSS in 1346 copies. `styles: {dedupe: 'link'}`
stores every distinct text once (`styleSheetStore`, keyed by a content hash) and writes
`<link rel="stylesheet" href="/swc-css/<hash>.css" data-swc-styles="...">` into the shadow roots instead. Serve the store
and put `head` (preload hints) into your page's `<head>`:

```ts
import {getStyleSheet, renderSpectrum} from 'spectrum-web-components-ssr/server';

app.get('/swc-css/:file', (req, res) => {
  const css = getStyleSheet(req.params.file.replace(/\.css$/, ''));
  if (css === undefined) return void res.status(404).set('Cache-Control', 'no-store').end();
  res.set('Cache-Control', 'public, max-age=31536000, immutable').type('text/css; charset=utf-8').send(css);
});

app.get('/', async (_req, res) => {
  const {html: markup, head} = await renderSpectrum(page(), {deferHydration: true, lang: 'en', styles: {mode: 'trimmed', dedupe: 'link'}});
  res.type('html').send(`<!doctype html><html lang="en"><head>${head}...</head><body>${markup}...</body></html>`);
});
```

It is off by default because browsers differ: Chromium waits in the parser for a shadow root's pending stylesheet link
and never paints unstyled content (a cold load renders progressively and finishes once the sheets arrived); Firefox
paints the content first and styles it when the sheet arrives - for a few frames even from a warm cache. The store is
per process and bounded (32 MiB LRU; a text a render linked is kept for at least 60 s, `minLifetimeMs`): with several
server instances, write the texts to shared storage through `dedupeUrl` (a `dedupeUrl` that throws keeps that text
inline and reports it). Minified theme sheets, sheets under 160 bytes and sheets with relative URLs (`url()`,
`@import`, `image-set()`, `src()`) stay inline.
`spectrum-web-components-ssr/client` handles the links like the server `<style>` elements. Sizes and the measurements: docs/API.md "Styles"
and docs/DESIGN.md "Style de-duplication" in the repository.

### Performance

A render is synchronous CPU work, queued one at a time per process, and the whole page is rendered before
`renderSpectrum()` resolves. Measured on a 15 W laptop CPU (0.3.0; 0.2.1 in brackets): the button page 21 ms (30 ms),
the picker page 48 ms (62 ms), the 1349-element catalog page 1.9 s (3.8 s) in `full` mode and 2.2 s (2.5-2.6 s) trimmed
or minified - about 0.65-1.6 ms per element. The output is identical to 0.2.2 apart from generated ids. Heap after GC
stays flat over repeated renders (111-114 MB for the catalog). A long render blocks its process's event loop (rendering
in `worker_threads` workers is not tested here). Serve the HTML compressed - brotli if you can: its window spans the
stylesheet copies of the shadow roots (button page 1253 KB -> 44 KB), gzip's 32 KB window does not (121 KB).

### Adapters

Everything specific to one component lives in an adapter. Built in: `sp-theme`, `sp-overlay` (kept closed), `sp-picker`,
`sp-breadcrumbs`, `sp-split-view`, `sp-color-wheel`, and `sp-table` (server-rendered selection checkbox cells). Register
your own, or replace a built-in one (the last registration for a tag wins):

```ts
import {registerAdapter} from 'spectrum-web-components-ssr/server';

registerAdapter({
  tag: /^my-/, // a tag name or a RegExp
  lifecycle: 'connected', // cap for matching elements
  prepare(element, ctx) {}, // every pass, right after the instance exists, before attributes and lifecycle
  beforeRender(element, ctx) {}, // pass 2 and later, before render()
  afterRender(element, ctx) {}, // pass 2 and later
  handlesMutation(element, target, operation, node) {}, // true when the adapter reproduces this DOM change
  lightDomInsertions(element) {}, // {target, value, position?: 'afterbegin'} entries rendered by a supplemental two-pass render
});
```

`ctx` carries `pass`, `id`, the structural `key`, the `ServerTree` and the element's `report` entry. The full contract is
in [docs/API.md](../../docs/API.md) of the repository.

## Browser

```ts
import 'spectrum-web-components-ssr/client'; // FIRST import of the client bundle: before lit and before any Spectrum module
import {hydrateSpectrum} from 'spectrum-web-components-ssr/client';
import '@spectrum-web-components/theme/sp-theme.js';
import '@spectrum-web-components/theme/src/themes.js';
import '@spectrum-web-components/button/sp-button.js';

const report = await hydrateSpectrum(document.getElementById('app')!);
// report: {errors, warnings, deferred, hydratedCount, durationMs}; hydrateSpectrum never rejects
```

`spectrum-web-components-ssr/client` must be evaluated before `lit`: it installs Lit's hydration support, which `lit-element` reads once,
when the `LitElement` class is created. Evaluate it later and elements ignore `defer-hydration` and re-render their
declarative shadow root from scratch (visible flicker). It also applies the declarative shadow DOM polyfill
(`@webcomponents/template-shadowroot`) when the browser lacks native support.

Two ways to hydrate, chosen by the `template` option:

* **With the Lit template** (the page is a Lit template, rendered by the same template on the server):
  `hydrateSpectrum(root, {template})` calls `hydrate(template, root)` from `@lit-labs/ssr-client`. The template must equal
  the one rendered on the server.
* **Without a template** (framework-agnostic: Angular, plain HTML, anything that produced the markup):
  `hydrateSpectrum(root)` removes `defer-hydration` top-down in document order, after `customElements.whenDefined` for
  the tags it finds. Elements without a `sp-` prefix that were server-rendered, such as `<overlay-trigger>`, are
  included. Tags that never get defined, such as an Angular component host `<app-root>`, are not awaited.

`registerHydrationAdapter({tag, beforeHydrate, afterHydrate, slotchangePlan})` is the client twin of the server adapters:
code around an element's first ("hydrating") update. Built in: `sp-picker`, `sp-slider`, `sp-breadcrumbs`, `sp-checkbox`,
`sp-table` (adopts server-rendered selection cells), a `matchMedia` adapter for every hydrating element that has
`MatchMediaController`s (`sp-picker`, `sp-action-menu`, `sp-contextual-help`, subclasses of them under other tags, your
own components), and a `Menu` adapter that lets menus hydrated long after their definitions loaded finish updating (so
`hydrateSpectrum()` may run late, e.g. after an Angular bootstrap).

`hydrateSpectrum(root, {removeServerStyles: true})` frees the `<style>` elements of the server-rendered shadow roots once
the elements have adopted the same CSS as constructable stylesheets (one shared sheet per component class instead of one
copy per instance). Trimmed server CSS is replaced either way (see [Smaller pages](#smaller-pages-trimmed-css)).

Server output rendered with `deferHydration: true` hydrates its light-DOM elements in document order, which is the order a
client-side render creates them in. Bundling: the e2e suite bundles the client with esbuild and the production conditions
of Lit (no `development` condition); the development builds of Lit are not covered by the tests.

### Angular SSR

Angular's server renderer (`@angular/ssr`, Angular 20) does not use Lit: Spectrum elements in its output are plain
elements without a shadow root. The integration below renders them in a post-processing step and hydrates them without
a Lit template, after Angular's own hydration. It is taken from a production application (Angular 20.1 with
`@angular/ssr` 20.1, `NgModule`-based, zoneless, Express 5); what the package's tests cover is the template-free
hydration path (`tests/agnostic.spec.ts`, `?agnostic=1` in the demo), not Angular itself. The pieces, in the order a
request meets them:

**Dependencies.** `package.json` names the package, the Lit peers and `@angular/ssr`:

```json
"@angular/ssr": "20.1.6",
"@lit-labs/ssr": "4.1.0",
"@lit-labs/ssr-client": "1.1.8",
"@lit-labs/ssr-dom-shim": "1.6.0",
"@spectrum-web-components/bundle": "1.12.4",
"express": "^5.1.0",
"lit": "3.3.3",
"lit-element": "4.2.2",
"lit-html": "3.3.3",
"spectrum-web-components-ssr": "^0.3.1"
```

**`angular.json`.** The application build gets a server entry and the Express entry. `@lit-labs/ssr-dom-shim` stays
external so that both server bundles (see below) share the one copy in `node_modules`; the package itself is bundled
into the application's server bundle, so it patches the same Lit classes the application's elements are built on.

```json
"server": "src/main.server.ts",
"outputMode": "server",
"ssr": {"entry": "src/server.ts"},
"polyfills": ["@angular/localize/init"],
"externalDependencies": ["@lit-labs/ssr-dom-shim"]
```

**Two bundles, one handover.** `@angular/ssr` builds `server.mjs` (the Express entry) and `main.server.mjs` (the
application) as separate bundles; the dev server loads both through its own module runner. The Spectrum renderer must
live in the application bundle (where the element classes are), so `main.server.ts` registers it on a global for
`server.ts`:

```ts
// ssr-bridge.ts
export const SPECTRUM_SSR = Symbol.for('my-app.ssr.spectrum');
```

**`main.server.ts`: the shim first, everything else dynamically.** With static imports the bundler may evaluate Lit or
Spectrum modules (in shared chunks) before the shim, so every module that imports them is loaded with `import()` after
the shim is installed. Two details of the shim matter here: Lit's DOM shim replaces `globalThis.fetch` with `node-fetch`,
whose Node-stream bodies Angular's `FetchBackend` cannot read, so native `fetch` is put back; and the shim's
`HTMLElement` must exist before `lit` is evaluated, because `ReactiveElement` extends the global `HTMLElement` it finds
then (Angular's server polyfills otherwise set Domino's).

```ts
// spectrum-dom-shim.ts
const nativeFetch = globalThis.fetch;
const {installSpectrumDomShim} = await import('spectrum-web-components-ssr/dom-shim');
installSpectrumDomShim();
globalThis.fetch = nativeFetch;
export {};
```

```ts
// main.server.ts
import './spectrum-dom-shim';
import {SPECTRUM_SSR} from './ssr-bridge';

// Your own element registry wrapper / overrides first, if you have one, then the application and the renderer.
const [{AppServerModule}, spectrumSsr] = await Promise.all([import('./app/app.module.server'), import('./spectrum-ssr')]);
globalThis[SPECTRUM_SSR] = spectrumSsr; // server.ts renders the Spectrum elements of every page with it
export default AppServerModule;
```

```ts
// spectrum-ssr.ts: the HTML Angular produced, rendered as a static Lit template
import {renderSpectrum} from 'spectrum-web-components-ssr/server';
import {html} from 'lit';
export {getStyleSheet} from 'spectrum-web-components-ssr/server';

export function renderSpectrumMarkup(markup: string, lang: string) {
  const strings = Object.assign([markup], {raw: [markup]}) as unknown as TemplateStringsArray;
  return renderSpectrum(html(strings), {deferHydration: true, lang, styles: {dedupe: 'link'}});
}
```

A static template carries attributes only, not Angular's property bindings (next point), and fragments only, not whole
documents. `dedupe: 'link'` is what keeps pages with long menus small: with inline styles the pickers of one search page
repeated the same sheets hundreds of times (16 MB).

**Bound properties become attributes before serialization.** Angular binds custom element inputs as DOM properties
(`[selected]`, `value="{{x}}"`, `[formControl]`), and the server DOM does not serialize properties, so the Spectrum
render would otherwise see default values; Lit's hydration does not correct values that differ from the server markup.
A `BEFORE_APP_SERIALIZED` hook writes every bound property of a Lit element that has an attribute as that attribute,
converted the way Lit reflects it:

```ts
// app.module.server.ts
providers: [
  provideServerRendering(withRoutes(serverRoutes)),
  {provide: BEFORE_APP_SERIALIZED, multi: true, useFactory: () => {
    const document = inject(DOCUMENT);
    return () => reflectCustomElementProperties(document);
  }},
]
```

```ts
// reflect-custom-element-properties.ts (server only)
export function reflectCustomElementProperties(document: Document): void {
  for (const element of Array.from(document.querySelectorAll('*'))) {
    if (!element.localName.includes('-')) continue;
    const ctor = customElements.get(element.localName) as LitElementClass | undefined;
    if (!ctor?.observedAttributes) continue; // also finalizes the class, which fills elementProperties
    for (const name of Object.keys(element)) {
      const options = ctor.elementProperties?.get(name);
      if (!options || options.state || options.attribute === false) continue;
      const attribute = typeof options.attribute === 'string' ? options.attribute : name.toLowerCase();
      const toAttribute = typeof options.converter === 'object' && options.converter.toAttribute || defaultToAttribute;
      const value = toAttribute(element[name], options.type); // defaultToAttribute: Lit's defaultConverter.toAttribute
      if (value == null) element.removeAttribute(attribute);
      else element.setAttribute(attribute, String(value));
    }
  }
}
```

**`server.ts`: render after Angular, fall back to Angular.** The Express handler lets Angular render, then replaces the
`<app-root>` of an HTML response with the Spectrum render of that markup, adds the stylesheet hints to `<head>`, and
serves the linked stylesheets. Any failure logs and returns Angular's output unchanged.

```ts
import {SPECTRUM_SSR} from './ssr-bridge';
import {AngularNodeAppEngine, createNodeRequestHandler, isMainModule, writeResponseToNodeResponse} from '@angular/ssr/node';
import express from 'express';

const spectrumSsr = () => globalThis[SPECTRUM_SSR] as typeof import('./spectrum-ssr') | undefined;
const appRootPattern = /<app-root\b[^>]*>[\s\S]*?<\/app-root>/i;
const htmlLanguagePattern = /<html\b[^>]*\blang=["']([^"']+)["']/i;

async function renderSpectrumComponents(response: Response): Promise<Response> {
  if (!response.headers.get('content-type')?.includes('text/html')) return response;
  const angularHtml = await response.text();
  const appRoot = angularHtml.match(appRootPattern)?.[0];
  if (!appRoot) return responseWithBody(response, angularHtml);
  const lang = angularHtml.match(htmlLanguagePattern)?.[1] ?? 'en';
  try {
    const spectrum = await spectrumSsr()!.renderSpectrumMarkup(appRoot, lang);
    for (const element of spectrum.report.elements) {
      if (element.errors.length) console.error(`Spectrum SSR: <${element.tagName}>`, element.errors.join('\n'));
    }
    let html = angularHtml.replace(appRoot, () => spectrum.html);
    if (spectrum.head) html = html.replace('</head>', () => `${spectrum.head}</head>`);
    return responseWithBody(response, html);
  } catch (error) {
    console.error('Spectrum SSR post-render failed; returning Angular SSR output.', error);
    return responseWithBody(response, angularHtml);
  }
}

// responseWithBody(response, body): a copy of the Response with the new body and without content-length

app.get('/swc-css/:file', (req, res, next) => {
  const css = spectrumSsr()?.getStyleSheet(req.params['file'].replace(/\.css$/, ''));
  if (css === undefined) return next();
  res.type('css').set('Cache-Control', 'public, max-age=31536000, immutable').send(css);
});

app.use((req, res, next) => {
  angularApp.handle(req)
    .then(response => response ? renderSpectrumComponents(response) : null)
    .then(response => response ? writeResponseToNodeResponse(response, res) : next())
    .catch(next);
});
```

The page language comes from `<html lang>` of the Angular output, so `index.html` carries the real one
(`<html lang="sr-Latn-ME">`): the renderer formats numbers and picks labels from it.

**`main.ts`: hydrate after Angular is stable.** The client entry is imported first, Angular is bootstrapped through a
dynamic import (so Lit and the Spectrum definitions evaluate after it, not in a shared chunk that runs earlier), and
Spectrum hydrates once Angular has claimed the DOM. Some elements render into their light DOM (`sp-textfield` without a
shadow root), which must not change before Angular's hydration has matched those nodes; a timeout keeps the page usable
if the app takes long to become stable.

```ts
import {hydrateSpectrum} from 'spectrum-web-components-ssr/client'; // must stay the first import
import {ApplicationRef} from '@angular/core';
import {platformBrowserDynamic} from '@angular/platform-browser-dynamic';

const angularHydrated = (appRef: ApplicationRef) =>
  Promise.race([appRef.whenStable(), new Promise(resolve => setTimeout(resolve, 5000))]);

import('./app/app.module')
  .then(({AppModule}) => platformBrowserDynamic().bootstrapModule(AppModule, {ngZone: 'noop'}))
  .then(moduleRef => angularHydrated(moduleRef.injector.get(ApplicationRef)))
  .then(() => hydrateSpectrum(document.body, {removeServerStyles: true}))
  .catch(error => console.error(error));
```

`AppModule` provides `provideClientHydration(...)` and imports the Spectrum definitions (`import './spectrum-imports'`,
one module listing every `sp-*.js` registration and icon the application uses; the server bundle imports the same
module, so both sides define the same elements).

## Limitations

* **Process-wide state.** `installSpectrumSsr()` installs browser-like globals for the whole process and never removes
  them (scoping them to a render is not feasible). Renders are serialized in one queue.
* **Late work after a render.** Some Spectrum code keeps running asynchronously (a disabled `sp-slider`'s
  `handleDisabledChanged()`, `sp-action-menu`'s `manageSelection()`). Rejections that arrive while the render runs become
  report warnings. Later ones from component hooks print a `SWC_SSR_LATE_REJECTION` process warning (they do not crash
  the server); later ones from anything else the render started - e.g. a client, interval or pool your code first
  created during a render - get Node's normal behaviour (by default the process exits). An application with its own
  `unhandledRejection` listener (or a `node:test` runner) sees all of them and decides itself. The package installs
  one `unhandledRejection` listener with the first render. Animation frames and `document` listeners such late work
  adds are dropped / removed: they never run inside another render.
* **Layout-dependent state is approximated.** Tabs indicator, color handles and split-view sizes are computed without
  layout and corrected after hydration (`sp-tabs` 0.069 %, `sp-color-area` 0.174 %, `sp-split-view` 0.057 % changed
  pixels in the matrix).
* **Phones.** The server's `matchMedia` never matches, so the server always renders the desktop state. Phones hydrate it
  without a mismatch and re-render into the mobile state (tray, `mobile-view`, modal contextual help) on the next update.
* **Known differences from a client render:** `sp-picker` and `sp-breadcrumbs` put the
  roving `tabindex="0"` on the selected menu item after hydration (a client render puts it on the first item);
  `sp-swatch` carries an extra `focusable` attribute on the selected swatch.
* **Locale.** Pass `lang` (or set `<sp-theme lang>`); otherwise numbers format as `en-US`.
* **Generated ids.** Module-level counters in Spectrum (`sp-dialog-label-N`) make the first and later renders of one
  process differ slightly in a few ids, and ids that components generate outside the synchronous parts of a render
  (e.g. `sp-field-label` / `sp-dialog` label ids assigned from a slotchange handler) come from the CSPRNG, so they
  differ between renders (the fidelity checks of the test suite normalize generated ids).
* **Browsers.** The Playwright suite runs in Chromium only.
* **Lit versions.** The package imports `lit-element/private-ssr-support.js` and `lit-html/private-ssr-support.js`; those are
  private to Lit, so keep `lit` within the declared peer range. `@lit-labs/ssr` is pinned to 4.1.x (see Install).

## Building and publishing this package

The workspace manifest exports TypeScript sources (`./src/*.ts`) so the demo and the tests run through `tsx` without a
build. The published form exports `./dist/*.js` with `types` conditions. `scripts/` in the repository switches between them:

```sh
npm run build:pkg        # tsc -p packages/swc-ssr/tsconfig.build.json -> packages/swc-ssr/dist (gitignored)
npm run pkg:verify       # builds, packs, installs the tarball into a scratch dir, renders and type-checks from it, cleans up
npm run pkg:prepare      # package.json exports -> ./dist (backup: package.json.orig); add "-- --name <npm-name>" to rename + make public
npm run pkg:restore      # back to the workspace manifest, byte for byte
npm run clean:pkg        # delete dist
```

Release checklist: replace the `REPLACE_WITH_OWNER` placeholders in `package.json`, `npm run pkg:verify`, then

```sh
npm run build:pkg
node scripts/prepare-publish.mjs --name spectrum-web-components-ssr
npm publish ./packages/swc-ssr --access public --dry-run   # drop --dry-run to publish
npm run pkg:restore
```

`sideEffects` lists the whole `dom-shim`, `client` and `server` directories: all of them install globals or register
adapters when evaluated, so they must survive tree shaking.
